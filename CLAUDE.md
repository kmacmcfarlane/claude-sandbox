# CLAUDE.md

## Project Overview

Docker-based sandbox for running Claude Code with filesystem isolation and opt-in host access (Docker socket, AWS, git, SSH, package caches — via CLI flags, env vars, or `.claude-sandbox/config.yaml`). Part of the [claude-kit](https://github.com/kmacmcfarlane/claude-kit) ecosystem.

## Key Architecture

- **Same-path mounting:** Container sees the project at its real host path so `docker compose` volume resolution works correctly against the host daemon.
- **Go implementation, spec-driven:** the CLI is a single Go binary (`cmd/claude-sandbox`, packages under `internal/`). Behavior is specified in `spec/*.feature` (Gherkin, stable scenario IDs like `CS-INIT-014`); every Ginkgo test references the scenario it implements, and `scripts/check-spec-coverage.sh` fails when a scenario has no referencing test. **Change the spec first, then the code+tests.** `bin/claude-sandbox` is a thin bash shim that rebuilds the binary when sources are newer (host `go` if present, else `docker run golang` with persistent build/module caches under `bin/dist/`) and execs it. In-container, the same binary is invoked as `ralph` (argv0 symlink).
- **Foreign-path resolver (`internal/paths`):** the SINGLE place that maps "foreign" files. Each logical path (config, dockerfile, env, ralph, agent, scripts) resolves to a single location under `.claude-sandbox/` (`config.yaml`, `Dockerfile`, `env`, `ralph/`, `agent/`, `scripts/`). No hardcoded foreign paths should live anywhere else. On launch, when `.claude-sandbox/` exists (and for greenfield ralph runs, which create it), the host sets up the layout: it creates the `temp/`/`reports/` skeleton, seeds `.claude-sandbox/CLAUDE.md`, and — per `trackInHost` — either gitignores `/.claude-sandbox/` + inits an internal sidecar git repo (`false`, default) or gitignores `env`+`temp/`+`ralph/` (ephemeral) while the host tracks the rest of the dir (`true`) — and in BOTH modes adds `.claude/worktrees/` (Claude Code's harness-native worktrees) to the same prompt, idempotently, skipped when an existing `.claude/`-style rule already covers it (CS-LAY-017). When `trackInHost` is `true` but the host already ignores the whole dir or a sidecar `.git` exists, the `true`-mode entries are refused with a warning naming the remedies (they would be dead under the ignore) — modes are never switched silently (CS-LAY-018); the mirror case — `trackInHost` `false` while the host already tracks files under the dir (`git ls-files`) — skips the `/.claude-sandbox/` line and the sidecar init with one warning naming both remedies, still proposing `.claude/worktrees/`, and a failed probe keeps the old behaviour; both conflict checks ask `git check-ignore` about a never-existing child (`.claude-sandbox/ignore-probe`), because git never reports a dir holding tracked files as ignored (CS-LAY-020). The child Dockerfile build **context stays the project root** even though the Dockerfile lives in `.claude-sandbox/`. The legacy scattered-root layout is no longer supported — see `docs/MIGRATION.md`.
- **Bootstrap subcommands (`init` / `init-ralph`):** these are positional subcommands (first arg), not flags — they bootstrap the project and exit, and reject launcher/claude flags (their own options: `--track-in-host`/`--no-track-in-host`, `--gitignore`/`--no-gitignore`, `--copy-parent-dockerfile`/`--no-copy-parent-dockerfile`, `--yes`). `init` seeds the **base** bootstrap files from the embedded `scaffold/` tree — `config.yaml`, `env.example`, and `Dockerfile.example` (optional, inactive until renamed; a copy of the nearest parent `.claude-sandbox/Dockerfile` when one exists, unless `--no-copy-parent-dockerfile`; the generic scaffold otherwise — no prompt) — then runs the layout setup, writing the host `.gitignore` entries the resolved `trackInHost` implies without a further prompt (`--no-gitignore` skips them; the launch-time "Add them?" prompt is unchanged), and exits without launching. A greenfield interactive `init` asks exactly one question, `trackInHost` (CS-INIT-028/029). `init-ralph` additionally seeds the **ralph** tree from the embedded `scaffold-ralph/` (`agent/` + `scripts/`) into `.claude-sandbox/`. Both are **idempotent** — existing files are never overwritten (so a project template's own docs win, and `init-ralph` fills only the gaps). The seeded `config.yaml` is **sparse (fully commented)** so it overrides nothing in the cascade, and init **never creates a real `env`** — it seeds `env.example`, a template the launcher never reads, lints or lists (CS-INIT-004/030, CS-CASC-030), so nothing project-level shadows an upstream env (a hand-filled project env once hid four upstream token refreshes); an existing project `env` is kept and reported (`kept     env (exists; its keys override upstream env)`); with no env anywhere but the project's own `env.example`, launch prints one `Note:` line instead of the missing-env warning (CS-LNCH-056), and `env.example` is never gitignored (CS-LAY-019); `trackInHost` is written explicitly (flag/prompt) unless an upstream config already defines it — then the prompt defaults to inheriting (Enter writes nothing locally and the commented hint records the inherited value + source; an explicit answer writes a local override). Both scaffold trees are **embedded in the binary** (`assets.go`), so `init` works from a bare binary; the seeded `scripts/` run in-container against the image's pre-installed `ruamel.yaml`. The `scaffold-ralph/agent/` docs are project-type-**agnostic baselines** — project-specific overrides live in `claude-templates` and take precedence when a template is applied first. Behavior spec: `spec/init.feature`, `spec/init-ralph.feature`.
- **Baked-in binary:** the Go binary (built in a multi-stage `golang` layer) and `logstream/` are copied into the Docker image at `/opt/claude-sandbox/`, not volume-mounted. `/opt/claude-sandbox/bin/ralph` is a symlink to the binary (argv0 selects ralph mode).
- **Host user identity:** `entrypoint.sh` renames the container `claude` user to the host caller's username/home directory and adjusts UID/GID to match. This ensures file ownership is correct and that absolute paths (e.g. plugin `installPath` values in `installed_plugins.json`) resolve identically inside and outside the container. The entrypoint also recursively chowns the home directory (skipping bind-mounted host paths discovered via `/proc/self/mountinfo`) so that files created as root during `docker build` are owned by the runtime user.
- **Home directory convention:** The base image provides `/home/claude` as the home directory. Child Dockerfiles should use `/home/claude` (not a hardcoded host path like `/home/yourname`) for portability. Use `USER claude` for `RUN` steps that create files under the home dir, and end with `USER root` so the entrypoint has privileges for UID/GID remapping. At runtime, the entrypoint moves build-time files from `/home/claude` to the host home path (e.g. `/home/rt`), skipping anything already present (bind mounts are never overwritten), then symlinks `/home/claude → $TARGET_HOME` so hardcoded paths still resolve.
- **Container naming (`imagebuild.ProjectSlug`):** `claude-sandbox-{parent}-{base}-{h6}-{instance}` (ralph: `…-{h6}-ralph`, no instance). The basename alone used to name the container, so the dozens of directories that share a name in a workspace all collided and only one could run. The parent segment keeps the common case readable; the `h6` digest of the absolute path makes every case correct. `Slug()` remains the plain character normalizer. That absolute path is always the **physical** one — `resolveProjectDir` evaluates symlinks on the `PROJECT_DIR` and working-directory branches alike (CS-LNCH-048), so a checkout reached through a symlink is one project with one slug, one instance-noun pool, one fingerprint and — because the same-path mount uses it — one Claude Code transcript slug rather than a split history `--resume` cannot see across; the config/env cascade walk and the child Dockerfile parent search climb the physical parents, so a workspace-level `.claude-sandbox/` beside the symlink is not seen; the launcher prints `Project: <physical> (resolved from <logical>)` when they differ.
- **Multi-session (`internal/sessions`):** a project can host several sessions. Discovery is by **container label**, never by parsing names (they are lossy — normalized and hashed), which also decouples discovery from the naming scheme. One label-filtered `docker ps --format '{{.Label "..."}}'` yields names, status and all labels with no per-container `inspect`; `docker top` adds the live-claude count so joined sessions are visible; the attachable process is found by matching those pids against `State.Pid` (PPID is the shim for all of them and the TTY column is `?` unless `-t`). Instance nouns are sampled **without replacement** from the nouns not already in use by the project, which is why a 128-word list needs no numeric tail. Three mechanisms, with different durability: a new container (PID 1, reattachable, survives terminal loss), a joined session (`docker exec`, cheap, **unrecoverable** and dies with the container's primary because of `--rm`), and attach (`docker attach`, recovery path). **Launch reservation (CS-SESS-048..054, CS-LNCH-057):** a new container is never `docker run`; every launch (interactive, ralph, `--branch`, the `[b]` fork) runs `docker create` with the full flag set (`Plan.Reserve`/`CreateArgs`), then `syscall.Exec`s `docker start -ai --detach-keys=K <name>` (`Plan.Start`; measured identical to `run` for stdio, exit code, SIGTERM cleanup and `--rm`). The split exists because nouns and pid classes are picked from discovery and a container was invisible to discovery until `docker run` had it running, so two concurrent launches could pick one noun (the second failed on the name) or one class (silently overwriting a peer-registry record). The picks and the create run in one critical section under a host-wide `flock` on `~/.cache/claude-sandbox/launch.lock` (`launch.FileLock` behind the `launch.HostLock` seam, `Env.Lock`; host-wide because classes are): `DiscoverAll`, remove `created` containers older than 60 s (orphans of a launcher that died between the steps — `--rm` never fires for a container that never started; plain `docker rm`, never `-f`), re-validate the EARLY noun (picked before the image build because it names the worktree in the banner; re-picked, with name/label/worktree re-derived and the banner reprinted, when a concurrent launch took it; `--worktree=NAME` and ralph's fixed name keep theirs), pick the class, `docker create`; discovery there is `DiscoverAllUncounted` (no per-sandbox `docker top` in the critical section). Released after create and before the exec (the fd is also `O_CLOEXEC`, Go's default), and **never held across image builds**. A create `Conflict` (a non-locking actor) re-picks and retries, 3 attempts total, then exits 2; ralph fails on the first unless the holder is itself a `created` reservation older than 10 s (a `docker start` that failed after the exec — the launcher cannot clean up past its exec), which is removed and retried once; a younger holder may be a concurrent launch between its create and its start (the lock is released before the exec), so it is never removed (`sessions.Inspect`, `docker inspect --type container`, `{{.Created}}` is RFC 3339, not the ps layout). Only docker's name conflict (`Conflict. The container name`) counts — a bare "Conflict" would match `Conflicting options` flag errors. A lock that cannot be taken in 30 s warns and launches unserialized; the warning says names stay unique but pid classes are unprotected. The lock is host-wide only for launches run ON THE HOST: `~/.cache/claude-sandbox` itself is not mounted into sandboxes (only subdirectories — package caches, the peer registry), so launchers run inside different containers take different lock files; names stay unique through the create conflict retry, but pid classes can collide between concurrent in-sandbox launches (found in the live verification). Discovery is `docker ps -a --filter status=created --filter status=running --filter status=paused` (paused because plain `ps` always listed them — dropping them would free a paused session's pid class; `{{.State}}`/`{{.CreatedAt}}` are optional trailing fields, and CreatedAt is parsed from its first three fields only, since zones without a letter abbreviation render it numerically, e.g. `+1030 +1030`), so reservations count as in use for both pickers, while `Session.Reserved()` keeps them out of every candidate list (`Interactive`), the `sessions` listing (`Live`) and `docker top`. `docker exec` needs `-u` (it skips the entrypoint's gosu and the image ends `USER root`) but not `-w` (inherited via `Config.WorkingDir`). **PID classes (`internal/pidslot`, `spec/pidslot.feature`):** Claude Code's peer registry is keyed by pid (`~/.claude/sessions/<pid>.json`) and every container's `claude` was PID 7 (exec keeps the entrypoint's pid), so sandboxes overwrote each other's records. The launcher allocates a class in `[0,256)` without replacement across ALL running sandboxes on the host (`sessions.DiscoverAll` + `PickClass`, label `claude-sandbox.pidclass`, env `CLAUDE_SANDBOX_PID_CLASS`, excluded from the drift fingerprint); the entrypoint, joins and ralph iterations run through `claude-sandbox pidslot -- <cmd>`, which burns pids to `k−1 (mod 256)` and execs `tini -s`, whose FORK lands the command on the class. Read `ns_last_pid` with one `read(2)` — dash's `read` sees one digit and loops forever. Always on; every failure warns and execs directly.
- **Shared peer registry (CS-LNCH-049..055):** Claude Code keys peer discovery on `<config dir>/sessions/<pid>.json`, and each record carries the ABSOLUTE socket path its writer bound — `XDG_RUNTIME_DIR || CLAUDE_CODE_TMPDIR || os.tmpdir()` + `/cc-socks/<pid>.sock` — which a reader lists only if `connect()` to that exact path works from the reader's container. XDG_RUNTIME_DIR is unset in sandboxes and the launcher derives the tmpdir from the config dir (CS-LNCH-034), so two trees exporting different `CLAUDE_CONFIG_DIR`s hold disjoint registries AND advertise socket paths that exist only in their own containers. The opt-in, **default-off** cascade key `sharedPeerRegistry` bridges them with one fixed folder, `~/.cache/claude-sandbox/peers` (the `PackageCacheRoot` precedent — a free-form path could name one tree's own `sessions/`): its `sessions/` is mounted over the container's `<config dir>/sessions`, and the folder itself is mounted at the SAME path in every bridged container with `-e XDG_RUNTIME_DIR` pointed at it, so every session binds and advertises `~/.cache/claude-sandbox/peers/cc-socks/<pid>.sock` — valid in every bridged container. It points at the ROOT, not `cc-socks` (Claude Code appends that; a bundled LSP library drops `vscode-ipc-*.sock` directly under XDG_RUNTIME_DIR). XDG_RUNTIME_DIR outranks CLAUDE_CODE_TMPDIR for the socket path only, so **scratchpads do not move** — but the variable applies to the whole container, so anything else honouring it (dbus, gpg, podman, pulse, the LSP `vscode-ipc-*.sock`) also lands in the shared, host-persistent folder. Both mounts are **read-write**: every session writes its record and `bind()`s its socket, and `bind()` under a `:ro` bind fails with EROFS (`connect()` through one succeeds — verified live; the old "connect() fails" rationale was wrong). `peers/`, `sessions/`, `cc-socks/` and the registry DESTINATION are created `0700` as the invoking user before `docker create`, and the three launcher-owned ones are `chmod`ed to `0700` even when they pre-exist wider (`mkOwnedPeerDir`; `MkdirAll` leaves an existing mode alone; the destination under the user's config dir is not re-moded) — docker would make a missing bind source (or a mountpoint under the rw config-dir bind, which lands on the host) as root, and Claude Code refuses a socket dir whose ancestry is group/world-writable or foreign-owned, silently falling back to a container-private `/tmp/cc-socks-<uid>`; the destination is created only when `underSamePathMount` says so (a cascade `mounts:` entry may set `host != container`). The WHOLE bridge stands down for the session — no mounts, no `-e`, nothing created, no banner, one warning, the key-off argv and fingerprint (`assembleSharedPeerRegistry` returns whether it applied, and the fingerprint hashes that) — when an env file defines `XDG_RUNTIME_DIR` (`envFilesDefine`, since `-e` beats `--env-file`; the launcher never forwards the host's own) or when the worst-case socket path exceeds Claude Code's 103-byte limit (CS-LNCH-054/055). A registry-only bridge would be strictly worse than off: Claude Code drops peers whose socket it cannot reach, so the session would list nobody and be listed by nobody, while the overmount hid its own tree's registry. The bridge **replaces** rather than unions: a bind mount hides the real `<config dir>/sessions`, so every session to be seen must be opted in and relaunched (which also rewrites its record), and a bridged launch prints one `Peer registry: shared (…)` banner (the `Worktree:` precedent) because the key can arrive from a workspace config. Resolution is tri-state (`ResolveTristate`, `*bool` + `json:"-"`) so a falsy `CLAUDE_SANDBOX_SHARED_PEER_REGISTRY` can keep one session off a workspace-wide bridge; the fingerprint hashes the APPLIED value, so unset, explicit `false` and a stood-down session hash alike. No CLI flag. It IS in the drift fingerprint — unlike the model/worktree/pid class it is a property of the environment, and attach/join skip mount assembly (joins and ralph iterations inherit the container's XDG_RUNTIME_DIR). No collision handling is needed: `internal/pidslot` already allocates pid classes without replacement across all running sandboxes, so no two containers can write the same `<pid>.json` or bind the same `<pid>.sock`. The key crosses a work/personal boundary by design; only the operator knows which trees to bridge.
- **Headless mode (CS-LNCH-058..067, CS-SESS-055):** `claude-sandbox headless [launcher flags] [--] <claude args>` is the command an SDK client (Paseo's daemon, via the Claude Agent SDK) runs in place of `claude`: `["claude-sandbox","headless","--"]`, with the SDK's args appended after `--` and probes of `… --version` / `… auth status` (5 s timeout). An explicit positional subcommand, never auto-detected from a piped stdin — interactive launches must stay transparent. `MainWithEnv` routes it straight to `runHeadless` (the cobra command exists for help and completion); the grammar is `scanArgs(args, headless=true)`, where `--help`/`-h`/`--version` start the passthrough because they are claude's after `headless`, and `--ralph`/`--limit`/`--attach`/`--join`/`--branch` exit 2. **No TTY:** `Inputs.Headless` → `docker create -i` without `-t` (with `-t` docker merges the container's stderr into stdout and writes CRs, corrupting stream-json) and `docker start -ai` with no `--detach-keys` (a terminal feature; it would eat stream bytes) — still A's create/start path under the launch lock, so concurrent SDK sessions get distinct nouns and classes. **Stderr:** the Env copy has `Out = Err` for the whole run, so every launcher message (cascade, banners, builds, warnings) lands on stderr and stdout is claude's alone; this works in one move because every launcher message already goes through `env.Out`/`in.Out`/`imagebuild.Options.Out` and subprocesses get `/dev/null` unless given a writer — never add a bare `fmt.Print`/`os.Stdout` write on the launch path. **No prompts:** `prompt.Fixed` replaces the TTY prompter, because `prompt.TTY` decides interactivity by opening `/dev/tty`, which a daemon with a controlling terminal HAS (a 2-minute session prompt would hang it); `--new` is implied (no exit 3), the update check is off unless `--update`, and the post-build cache-budget check is skipped. **Env allowlist (`launch.HeadlessEnv`):** exactly `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING`, `CLAUDE_AGENT_SDK_{VERSION,CLIENT_APP,DISABLE_BUILTIN_AGENTS,MCP_NO_PREFIX}`, `PASEO_AGENT_ID`, `PASEO_AGENT_CWD`, each a bare `-e NAME` (value read by the `docker create` client from the launcher's inherited env, never in argv) and only when set (`Inputs.LookupEnv`); NEVER a prefix wildcard, because the Paseo daemon's env can hold `PASEO_PASSWORD`. Label `claude-sandbox.mode=headless` (`launch.ModeHeadless`): `sessions.Interactive` drops it, so it is never an attach/join/tier-1/completion candidate (a terminal attached to a JSON stream corrupts it), while the `sessions` listing SHOWS it with MODE `headless` and its noun and class stay taken. cwd is the physical cwd (CS-LNCH-048), which is also where Claude Code files the transcript the client reads — which is why headless IGNORES the cascade `worktree` key and `CLAUDE_SANDBOX_WORKTREE` (only an explicit `--worktree[=NAME]` in the prefix counts, `resolveWorktree(..., headless)`, CS-LNCH-066): a worktree files the transcript under another slug and each spawn would get a fresh noun, breaking `--resume=<id>`. **Dangerous mode is deliberately NOT ignored** (operator decision, CS-LNCH-067): a cascade `dangerous: true` gives every headless session `--dangerously-skip-permissions`, which Claude Code (measured on 2.1.277) lets win over `--permission-mode` in either order, plan included, so the client's permission picker is overridden; a project opts out with a more-local `dangerous: false` (scalar merge, more-local wins) — which also turns it off for that project's interactive launches; there is no headless-only opt-out — and `CLAUDE_SANDBOX_DANGEROUS=0` cannot (OR shape, a falsy env falls through). A bare `--worktree` in a client's prefix has the same resume problem (new noun, new worktree per spawn); `--worktree=NAME` avoids it but makes concurrent sessions share one worktree. Headless also never runs the post-build `WarnCacheBudget` (`docker system df` measured 5.7-6.3 s, past Paseo's 5 s probe timeout; CS-LNCH-062). Probes are full launches, so one that hits an image rebuild can still time out. Never list a daemon secret as a bare key in a cascade `env`: `--env-file` resolves bare keys from the launcher's (the daemon's) environment. The shim's build steps send their output to stderr for the same stdout reason. Paseo rollout (README): the BUILT-IN `claude` provider id gets the sandboxed command (Paseo has no default-provider setting, so a separate sandboxed provider would leave native as the default) and `claude-native` names `["claude"]` explicitly; Paseo's MCP tool injection stays off.
- **Detach keys:** default `ctrl-q,ctrl-q`, overridable via `detachKeys`, resolved in one place (`launch.ResolveDetachKeys`) and passed to **all three** interactive docker invocations — `start` (the primary session; it was `run` before the launch reservation split, and the keys go on `start -ai`, never on `create`, which attaches nothing), `attach` and `exec`. Omitting the flag does not mean "no detach keys", it means docker's own `ctrl-p,ctrl-q`, so a path that forgets it is silently wrong rather than obviously broken; that is exactly how `docker run` and `docker exec` were first shipped missing it while only `attach` had it. Docker's default is unusable here because the Claude Code TUI binds `ctrl+p`, along with nearly every other ctrl letter and `ctrl+]`/`ctrl+\`/`ctrl+_`; `ctrl-q`, `ctrl-^`, `ctrl-@` are the unbound ones. The stakes are highest on the exec path, where detaching orphans the session beyond recovery.
- **TTY is required, never defaulted:** when a session decision is needed and no terminal is attached, the launcher prints what it found and exits **3** (distinct from the generic 2). `prompt.Ask` returns `""` for Enter, EOF *and* no-tty alike, so a defaulted branch would silently change behavior for scripts. Bypass flags (`--new`, `--branch`, `--attach[=N]`, `--join[=N]`, `--no-session-check`, `--allow-config-drift`) remove the decision and so need no terminal. `--branch` launches a new container whose claude forks a conversation (`--resume --fork-session`, claude's own picker; compose with passthrough `--name` to name the fork; the tier-1 `[b]` choice forks the newest via `--continue --fork-session`) — composing upstream flags, never reading the version-unstable transcript files. `--no-session-check` skips the *decision*, not the instance-noun lookup — naming a container without knowing which nouns are taken would reintroduce the collisions this fixes.
- **Worktree mode (CS-LNCH-041..047, CS-SESS-045..047):** a launch can run claude with its own `--worktree <name>` (`<repo-root>/.claude/worktrees/<name>`, branch `worktree-<name>`; claude creates/reopens it and blocks edits to the shared checkout from inside). **Default: OFF for interactive launches, ON for ralph.** Claude Code files transcripts by working directory, so a worktree has its own empty history and `--resume` there lists none of the repo's conversations — the mode shipped on-by-default for everyone and was flipped after that empty picker cost an operator a conversation; an interactive launch must be transparent, an unattended ralph run should be isolated. Any default a user must discover by losing something is the wrong default. The name is the instance noun (`ralph` for ralph; `--worktree=NAME` overrides and deliberately reopens), so the noun picker also skips nouns whose worktree directory already exists. Precedence is **tri-state** (`launch.ResolveTristate`, CLI `--worktree`/`--no-worktree` > `CLAUDE_SANDBOX_WORKTREE` with `0/false/no` an explicit off > cascade key `worktree` > per-kind default) — the OR shape of `dangerous` cannot express "off" over ralph's true default. The banner prints only when a worktree is in use or a requested one stood down, never to narrate the shared-checkout default. Per-session choice like the model: `cascade.Config.Worktree` is `json:"-"` and `Inputs.Worktree` is excluded from the fingerprint; label `claude-sandbox.worktree` (empty when off) feeds the `sessions` WORKTREE column, attach reports it, join runs bare `--worktree` (claude names it — two sessions must not share one worktree), `--branch` composes `--worktree <new-noun>` with `--resume|--continue --fork-session` — both only when the mode resolves on. `launch.GitRoot` (`git rev-parse --show-toplevel`) gates it: outside a git work tree the launch stands down with a `Worktree: off (not a git repository)` banner, never a prompt or an error. The container always gets `CLAUDE_SANDBOX_PROJECT_DIR` so a session in a worktree can find `.claude-sandbox/`. Launcher-owned flags precede `--model` and passthrough; `-w` still passes through. **Ralph (CS-RLP-019..022):** one worktree per RUN — the loop forwards `--worktree <name>` to every iteration (reopen is claude's reuse path; `-p` never cleans up) while the loop itself stays at the project root (lock, stop file, runlog, prompts under `.claude-sandbox/`, which is gitignored and so absent from the worktree checkout); each iteration's claude gets `BACKLOG_REPO_ROOT` + `CLAUDE_SANDBOX_PROJECT_DIR` = project root, and a generated "Where you are" prompt block names the worktree/branch. **Ralph never merges into `main`**: the run branch `worktree-<name>` is the deliverable a human fast-forwards from. The scaffold-ralph docs address `.claude-sandbox/` through those env vars and route writes there via Bash (`backlog.py`, `touch`) because the harness blocks Edit/Write to the main checkout from a worktree. The legacy `scripts/worktree/` helper (`.worktrees/<id>`, `story/<id>`) is gone — there is one worktree convention.
- **Config drift (`internal/launch/fingerprint.go`):** attach/join deliberately skip the image check, mount assembly and shadow injection, so each container carries a `confighash` label over the **resolved** launch (merged cascade config, env file contents, Dockerfile+context, the image ID actually used, shadow-file contents, normalized mounts, host-access flags, host identity, memory limit) plus an `inputs` label of per-file digests to explain a mismatch. Hashing the resolved result rather than the argv is required — the shadow mounts (CLAUDE.md, .mcp.json, gitconfig) live in a per-launch temp dir, so an argv hash would differ every time — and rather than the raw files is better: an added upstream config counts as drift, a fully shadowed upstream edit correctly does not. Model/passthrough/`--limit`/instance/pid class/worktree are excluded as per-session choices; the model and the worktree are reported separately since attach cannot change them.
- **Fresh-context iterations:** Ralph runs Claude as a new process each iteration, not session continuation.
- **Container context injection:** `bin/claude-sandbox` builds a temp file by concatenating the host's `~/.claude/CLAUDE.md` (if any) with `container-context.md`, then bind-mounts it read-only over the config dir's `CLAUDE.md` in the container. This gives every session (interactive or ralph) awareness of the container environment without modifying the host file. For ralph loops, `PROMPT_RALPH.md` is additionally piped as part of the prompt.
- **Sibling file mounting:** The launcher mounts `.claude.json` from the parent of the config directory, mirroring the standard `$HOME/.claude/` + `$HOME/.claude.json` layout. When `CLAUDE_CONFIG_DIR` relocates the config dir, the same sibling relationship applies. This ensures global state works identically inside the container.
- **MCP server injection:** The launcher merges `mcp-servers.json` (sandbox-provided MCP servers like the Discord notifier) into the host's `~/.mcp.json` (via a throwaway `docker run` with Node), writes the result to a temp file, and bind-mounts it read-only over `.mcp.json` in the container. The host file is never modified. If no host `.mcp.json` exists, the sandbox fragment is used as-is.
- **Settings are live, hooks are managed (CS-LNCH-011, CS-LNCH-068):** `settings.json` is **not** shadowed — it reaches the container through the read-write config-dir bind, so user-scope writes from a sandbox (`/plugin install` → `enabledPlugins`, `marketplace add` → `extraKnownMarketplaces`, `/model`, `/effort`, permission rules) land on the host file and persist to the next sandbox. The per-launch shadow it replaced (a temp copy with `notification-hooks.json` merged over its top-level keys, bind-mounted rw) silently discarded every such write and replaced the host `hooks` object wholesale. `notification-hooks.json` is instead baked into the base image as a Claude Code managed-settings **drop-in**, `/etc/claude-code/managed-settings.d/10-claude-sandbox.json` (0644; a drop-in so a child can ship its own `managed-settings.json`), inherited by every child and cap, so every session path gets it with no per-launch file or argv. Hook entries merge across settings levels (code.claude.com/docs/en/hooks; verified on Claude Code 2.1.277), so host hooks run alongside. A `settings.json` that is a symlink gets its `filepath.EvalSymlinks` target bind-mounted rw at its own path unless a same-path mount already covers it (after the cascade mounts; a dangling link warns once) — the old shadow's `os.ReadFile` followed links, the config-dir bind does not, and a link dangling in the container makes Claude Code run with no user settings, logged only at debug (CS-LNCH-069); that mount is in the drift fingerprint via the normalized mount set. Trade-offs, accepted by the operator: sandbox sessions write the host `settings.json`, including `hooks` and permission `allow` rules that then run unsandboxed in host sessions; host hooks now also run in sandboxes, where a host-only binary fails; the managed source is named in `/status` and a user-level `disableAllHooks` cannot disable managed hooks; file-based managed settings are skipped when a server-managed (Team/Enterprise) policy applies. `notification-hooks.json` is a baked source (CS-IMG-004). The rest of the config dir stays read-write for sessions, credentials, and history.
- **Image layering (base → child → cap, plus a CLI image):** The base image (`claude-sandbox`, `Dockerfile`) provides sandbox infrastructure (OS, Node, Docker CLI + buildx, Python venv, sandbox binary) and deliberately **not** the Claude Code CLI. The CLI is installed by `Dockerfile.cli` into `claude-sandbox-cli`, pinned via `--build-arg CLAUDE_CODE_VERSION` (the installer's positional pin) to the version the update check resolved from npm. The image a container runs is a generated one-layer **cap**, `<base-or-child>:run` (`imagebuild.CapImageName`), built from a stdin Dockerfile: `FROM <under>` + two `COPY --link --from=claude-sandbox-cli` lines. So a Claude Code update rebuilds the CLI image and each project's cap on its next launch, never the base or a child — installing the CLI mid-base used to rebuild every child cold (≈3 min each for a 13 s install). The update check reads the CLI image's `claude-sandbox.claude-version` label (an inspect, not a `docker run`); `--rebuild` rebuilds all four; `sessions_cmd.wouldBeFingerprint` resolves the cap so a CLI update registers as drift. BuildKit is a hard prerequisite (`EnsureBuildKit` → exit 2 naming `docker-buildx-plugin`; every build gets `DOCKER_BUILDKIT=1`), and after any build `WarnCacheBudget` compares `docker system df` with the `buildx inspect` GC policy — the daemon evicts cache mounts once the ephemeral-records budget is exhausted. Base and CLI Dockerfiles use `RUN --mount=type=cache` with fixed ids (`claude-sandbox-{apt,apt-lists,pip,npm,go-mod,go-build}`) so children reusing the ids share one cache per package manager (`USER claude` steps need `uid=1000,gid=1000`). Child Dockerfiles must not invoke `claude` at build time. Projects place a `.claude-sandbox/Dockerfile` to add project-specific tools (Go, language servers, etc.) via `FROM claude-sandbox`. If not found in the project directory, the launcher walks parent directories (direnv-style) to find one — useful for monorepos or workspaces sharing a single child Dockerfile. The launcher builds the child image automatically, tagged `claude-sandbox-df-{context-dir-slug}-{h6}` where `h6` hashes the **(Dockerfile path, build context)** pair — the tag describes what the image was built *from*, not which project triggered it, so every project resolving one shared parent Dockerfile shares a single image instead of each rebuilding an identical copy under a colliding tag. The context is part of the identity because the default branch builds with the project root as context while `dockerfileDir` builds with the override dir. `ImageName` is therefore computed *after* Dockerfile resolution (`imagebuild.ImageSlug`), and is empty when no child is in use. Override the child Dockerfile location via `CLAUDE_SANDBOX_DOCKERFILE_DIR`/`CLAUDE_SANDBOX_DOCKERFILE` env vars or `dockerfileDir`/`dockerfile` keys in `.claude-sandbox/config.yaml`. Set `baseOnly: true` (or `CLAUDE_SANDBOX_BASE_ONLY=1`) to skip child Dockerfile detection.
- **Linked git worktrees (CS-LNCH-070..075, CS-CASC-031..033):** a project dir that is a linked worktree outside its repository (Paseo's `~/.paseo/worktrees/<id>/<name>`) used to lose the whole cascade — its physical parents never reach the main checkout, whose `.claude-sandbox/` is usually a gitignored sidecar absent from the worktree — and git in the container could not reach `<main>/.git`. `launch.DetectLinkedWorktree` runs ONE `git -C <dir> rev-parse --git-dir --git-common-dir --show-toplevel` (execx seam; unmatched in `execx.Fake`, so plain-launch tests see "not linked") and trusts the answer only when git dir != common dir, the git dir is `<common>/worktrees/<name>`, and git's back-link `<gitdir>/gitdir` names `<top>/.git` — the security gate for the rw mount: the `.git` file is data in the project tree, and only `git worktree add`/`repair` in THAT repository writes the back-link. A mismatched back-link warns (`git worktree repair`) and launches plain. Main = the common dir's parent when it is named `.git` (bare: none). `paths.Chain(start, main)` is the one search order (most-local first): start's ancestors not on main's chain, then main and its ancestors; `CollectChain`/`FindChain`/`FindChainFile`/`SandboxLevelsChain` walk it, and `CollectUp`/`FindUp`/`FindUpFile`/`SandboxLevels` are its `main == ""` form, so plain launches and harness worktrees (whose parents already include main) are unchanged. `ResolveChild` takes `MainCheckout`; a Dockerfile found in the main checkout builds with the main checkout as context, i.e. the image tag main-checkout launches already use. `Inputs.Linked` makes `Build` add `<common>:<common>` (rw) after the cascade mounts unless a same-path mount covers it, and only when the worktree top is under the project mount (not from a subdirectory); it reaches the fingerprint through the normalized mount set, and `wouldBeFingerprint` gets the same `linked` so attach/join do not see drift. Identity (slug, labels, `-w`, noun pool, `CLAUDE_SANDBOX_PROJECT_DIR`) stays on the worktree path — the main checkout is not mounted, so naming it in the container would name a missing path. One `Linked worktree:` banner line. No config key.
- **Config cascade (parent directory search):** `config.yaml` and `env` are resolved by walking parent directories from the project root (direnv-style) and **cascaded**: every `config.yaml` found root→project is deep-merged by `internal/cascade` (scalars/maps: more-local wins; `mounts`: append, same `host`+`container` overrides upstream), and every `env` is passed as stacked `--env-file` flags (later wins). The launcher prints the cascade at startup. The child `Dockerfile` is nearest-wins (whole file, no merging). This lets a workspace root provide catch-all defaults that sub-projects sparsely override.

## Ralph Runtime Directory

Ralph stores all runtime files under the resolved ralph directory — `.claude-sandbox/ralph/` (resolved by `internal/paths`). It contains only ephemeral state — never commit its contents directly (it is covered by the host gitignore / sidecar).

```
<ralph-dir>/                        # .claude-sandbox/ralph/
  stop                              # touch to halt the loop (checked each iteration)
  lock                              # PID lock preventing concurrent loops
  runlog.json                       # structured per-iteration metrics (persistent across runs)
  runlogs/                          # raw NDJSON stream logs
    rawlog_<YYYYMMDDHHmmSS>_iter<N> # one file per iteration (persistent)
  temp/                             # scratch space (wiped each iteration)
    quota-status                    # "ok", "quota_exhausted", or "rate_limit"
    stderr                          # captured stderr from claude process
```

- **Stop the loop:** `touch .claude-sandbox/ralph/stop`
- **Run metrics:** `<ralph-dir>/runlog.json` — array of runs with per-iteration duration, tokens, cost, story marker, and subagent details
- **Debug a run:** read the corresponding `<ralph-dir>/runlogs/rawlog_*` file for the full NDJSON stream
- **Do not store persistent state in `<ralph-dir>/temp/`** — it is wiped at the start of every iteration
- Prompt files live in the resolved agent directory — `.claude-sandbox/agent/`, e.g. `.claude-sandbox/agent/PROMPT.md` — these are inputs, not runtime outputs

## Development Notes

- **Workflow:** spec first (`spec/*.feature`, stable scenario IDs), then Ginkgo tests referencing those IDs, then implementation. Run `go test ./...` and `scripts/check-spec-coverage.sh` before considering a change done. Tests inject `execx.Fake` and `prompt.Scripted` — no docker/git/network in unit tests.
- The shim uses `readlink -f` to resolve symlinks and find the repo root; the binary honors `CLAUDE_SANDBOX_REPO_ROOT` (set by the shim) and otherwise derives it from its own location.
- Go deps are plain modules (no `vendor/`). The shim's `docker run golang` path persists `GOCACHE` and `GOMODCACHE` under `bin/dist/` (gitignored) so each dependency downloads once; the Dockerfile builder runs `go mod download` in its own cached layer.
- Base, CLI and child images auto-rebuild if their respective Dockerfiles are newer than the cached image. The base also rebuilds when any baked source (`cmd/`, `internal/`, `go.mod`/`go.sum`, `assets.go`, `logstream/`, `entrypoint.sh`, `PROMPT_RALPH.md`, `mcp/`, `notification-hooks.json`; `_test.go` files excluded, CS-IMG-031) is newer than the image — so editing a source picks up on the next launch without `--rebuild`. A base rebuild triggers a child rebuild; the cap rebuilds whenever its parent or the CLI image is newer. A CLI update rebuilds nothing but the CLI image and the caps.
- **Cache mounts and `--no-cache`:** a build run with `--no-cache` gets a FRESH cache mount, not the shared one — verified on Docker 29.3/BuildKit 0.28 (three ordinary builds accumulate state in one mount id; the same builds under `--no-cache` each start empty). So `--rebuild` discards the shared apt/pip/npm/go caches by design (CS-IMG-002). This, not GC, explains most "the cache mount was wiped" reports — check for `--no-cache` before investigating budgets.
- **Host-side hygiene:** two independent GC limits govern cache mounts — the `All: true` rule's total budget (pruning helps) and the `type==exec.cachemount` rule's cap (pruning does NOT help; it is a setting). `WarnCacheBudget` reports them as separate messages for that reason. The README "BuildKit cache" section carries the `docker builder prune -af` and the explicit `builder.gc.policy` recipe; `defaultKeepStorage` is the Desktop-era key and is ignored on engines that derive thresholds from disk size, and `builder.gc` needs a full daemon restart (SIGHUP does not reload it).
- **`packageCaches` lever** (`hostAccess.packageCaches` / `--package-caches`): mounts `~/.cache/claude-sandbox/{go-mod,go-build,npm,pip}` writable at the same path and sets `GOMODCACHE`/`GOCACHE`/`npm_config_cache`/`PIP_CACHE_DIR`. The launcher `MkdirAll`s them before `docker create` (Docker would create a missing bind source as root and the entrypoint never chowns mount points). The root is fixed (`launch.PackageCacheRoot`) and must never be pointed at the host's own caches — Go trusts extracted module dirs, so a session could otherwise poison the host toolchain.
- **Version stamping:** the launcher computes `git describe --tags --always --dirty` and passes it as the `CLAUDE_SANDBOX_VERSION` build-arg. The Dockerfile bakes it into `$CLAUDE_SANDBOX_VERSION`, `/opt/claude-sandbox/version`, and the `org.opencontainers.image.revision` image label. `claude-sandbox --version` prints the host-script version and the baked-image version (warns if they differ).
- Missing `.claude-sandbox/env` (no level of the cascade has one) logs a warning but doesn't fail; when the project's own `env.example` exists it is a single `Note:` line instead (CS-LNCH-056).
- `container-context.md` describes the base container environment and is merged into `~/.claude/CLAUDE.md` for all sessions (interactive and ralph). It covers base-image tools only; project-specific tools are discoverable at runtime. Keep it up to date when the base image changes.
- `README.md` is the user-facing documentation. Keep it up to date whenever you add, remove, or change features, CLI flags, pipeline stages, or directory structure.
- **Before considering any change done**, check whether `scaffold/config.yaml`, `scaffold/env.example`, or `README.md` need a corresponding update. Features, config keys, env vars, and behavioral changes should be reflected in all relevant places.

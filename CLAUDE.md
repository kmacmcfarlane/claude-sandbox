# CLAUDE.md

## Project Overview

Docker-based sandbox for running Claude Code with filesystem isolation and opt-in host access (Docker socket, AWS, git, SSH, package caches — via CLI flags, env vars, or `.claude-sandbox/config.yaml`). Part of the [claude-kit](https://github.com/kmacmcfarlane/claude-kit) ecosystem.

## Key Architecture

- **Same-path mounting:** Container sees the project at its real host path so `docker compose` volume resolution works correctly against the host daemon.
- **Go implementation, spec-driven:** the CLI is a single Go binary (`cmd/claude-sandbox`, packages under `internal/`). Behavior is specified in `spec/*.feature` (Gherkin, stable scenario IDs like `CS-INIT-014`); every Ginkgo test references the scenario it implements, and `scripts/check-spec-coverage.sh` fails when a scenario has no referencing test. **Change the spec first, then the code+tests.** `bin/claude-sandbox` is a thin bash shim that rebuilds the binary when sources are newer (host `go` if present, else `docker run golang` with persistent build/module caches under `bin/dist/`) and execs it as argv0 `claude-sandbox` (CS-TMUX-001: tmux-resurrect's process match). Its builds serialise on `flock bin/dist/.build.lock` (CS-TMUX-073): taken only when the binary is stale, staleness re-checked under it so waiters exec the holder's build, the wait bounded at 600 s (`CLAUDE_SANDBOX_BUILD_LOCK_WAIT` overrides; then build unlocked — a hung `docker run golang` must not hold every pane), fd 9 closed before the exec and for the build commands (by a bare `exec 9>&-` — any other redirection on that exec would stick to the launcher's stdio); no `flock` (macOS) = the old unlocked build, silently; every build, locked or not, writes a temporary file in `bin/dist/` (`.claude-sandbox.build.<shim pid>`) and `mv -f`s it over `bin/dist/claude-sandbox`, so that path is always a whole binary (`go build -o` across filesystems truncates and writes in place: ETXTBSY, or a half-written binary already newer than the sources), and a failed build removes its temporary file; the hook fast paths (`tmux save`, `tmux restore --pin|--rearm`, CS-TMUX-068) return before it, never building or waiting. In-container, the same binary is invoked as `ralph` (argv0 symlink).
- **Foreign-path resolver (`internal/paths`):** the SINGLE place that maps "foreign" files. Each logical path (config, dockerfile, env, ralph, agent, scripts) resolves to a single location under `.claude-sandbox/` (`config.yaml`, `Dockerfile`, `env`, `ralph/`, `agent/`, `scripts/`). No hardcoded foreign paths should live anywhere else. On launch, when `.claude-sandbox/` exists (and for greenfield ralph runs, which create it), the host sets up the layout: it creates the `temp/`/`reports/` skeleton, seeds `.claude-sandbox/CLAUDE.md`, and — per `trackInHost` — either gitignores `/.claude-sandbox/` + inits an internal sidecar git repo (`false`, default) or gitignores `env`+`temp/`+`ralph/` (ephemeral) while the host tracks the rest of the dir (`true`) — and in BOTH modes adds `.claude/worktrees/` (Claude Code's harness-native worktrees) to the same prompt, idempotently, skipped when an existing `.claude/`-style rule already covers it (CS-LAY-017). When `trackInHost` is `true` but the host already excludes the dir ITSELF (`git check-ignore -q --no-index -- .claude-sandbox`, no trailing slash; a children-only rule like `.claude-sandbox/*` is not a conflict because the `!` lines work beneath it, CS-LAY-021) or a sidecar `.git` exists, the `true`-mode entries are refused with a warning naming the remedies (they would be dead under the ignore) — modes are never switched silently (CS-LAY-018); the mirror case — `trackInHost` `false` while the host already tracks files under the dir (`git ls-files`) — skips the `/.claude-sandbox/` line and the sidecar init with one warning naming both remedies, still proposing `.claude/worktrees/`, and a failed probe keeps the old behaviour; the "new files are hidden" questions (the CS-LAY-020 incident warning, the sidecar init) ask `git check-ignore` about never-existing children, because git never reports a dir holding tracked files as ignored (CS-LAY-020) — two unlike names, `ignore-probe` and `ignore-probe.md`, both of which must be ignored, so whitelist-style (`*`/`!*/`/`!*.*`) or extension-only rules do not count (CS-LAY-022; a rule negating a probe name by hand defeats it, accepted). The child Dockerfile build **context stays the project root** even though the Dockerfile lives in `.claude-sandbox/`. The legacy scattered-root layout is no longer supported — see `docs/MIGRATION.md`.
- **Bootstrap subcommands (`init` / `init-ralph`):** these are positional subcommands (first arg), not flags — they bootstrap the project and exit, and reject launcher/claude flags (their own options: `--track-in-host`/`--no-track-in-host`, `--gitignore`/`--no-gitignore`, `--copy-parent-dockerfile`/`--no-copy-parent-dockerfile`, `--yes`). `init` seeds the **base** bootstrap files from the embedded `scaffold/` tree — `config.yaml`, `env.example`, and `Dockerfile.example` (optional, inactive until renamed; a copy of the nearest parent `.claude-sandbox/Dockerfile` when one exists, unless `--no-copy-parent-dockerfile`; the generic scaffold otherwise — no prompt) — then runs the layout setup, writing the host `.gitignore` entries the resolved `trackInHost` implies without a further prompt (`--no-gitignore` skips them; the launch-time "Add them?" prompt is unchanged), and exits without launching. A greenfield interactive `init` asks exactly one question, `trackInHost` (CS-INIT-028/029); its default is `false` unless the host repo already tracks files under `.claude-sandbox/` (`layout.HostTrackedCount`, CS-LAY-020's `git ls-files` probe), and neither hides new files there (`layout.DirIgnored`, any rule, children-only included) nor has a sidecar `.git`, when it is `true` and the preamble says why — `false` there would start the project in the CS-LAY-020 warning state; flags, an existing config and an upstream value never consult the probe (CS-INIT-031/032). `init-ralph` additionally seeds the **ralph** tree from the embedded `scaffold-ralph/` (`agent/` + `scripts/`) into `.claude-sandbox/`. Both are **idempotent** — existing files are never overwritten (so a project template's own docs win, and `init-ralph` fills only the gaps). The seeded `config.yaml` is **sparse (fully commented)** so it overrides nothing in the cascade, and init **never creates a real `env`** — it seeds `env.example`, a template the launcher never reads, lints or lists (CS-INIT-004/030, CS-CASC-030), so nothing project-level shadows an upstream env (a hand-filled project env once hid four upstream token refreshes); an existing project `env` is kept and reported (`kept     env (exists; its keys override upstream env)`); with no env anywhere but the project's own `env.example`, launch prints one `Note:` line instead of the missing-env warning (CS-LNCH-056), and `env.example` is never gitignored (CS-LAY-019); `trackInHost` is written explicitly (flag/prompt) unless an upstream config already defines it — then the prompt defaults to inheriting (Enter writes nothing locally and the commented hint records the inherited value + source; an explicit answer writes a local override). Both scaffold trees are **embedded in the binary** (`assets.go`), so `init` works from a bare binary; the seeded `scripts/` run in-container against the image's pre-installed `ruamel.yaml`. The `scaffold-ralph/agent/` docs are project-type-**agnostic baselines** — project-specific overrides live in `claude-templates` and take precedence when a template is applied first. Behavior spec: `spec/init.feature`, `spec/init-ralph.feature`.
- **Baked-in binary:** the Go binary (built in a multi-stage `golang` layer of `Dockerfile.tools`), `entrypoint.sh`, `logstream/`, `PROMPT_RALPH.md`, the Discord MCP bundle and the version file live under `/opt/claude-sandbox/` in the `claude-sandbox-tools` image, which the run cap copies in (CS-IMG-048/049) — not volume-mounted, and not in the base. `/opt/claude-sandbox/bin/ralph` is a symlink to the binary (argv0 selects ralph mode); the cap copies the directory whole so the link survives.
- **Host user identity:** `entrypoint.sh` renames the container `claude` user to the host caller's username/home directory and adjusts UID/GID to match. This ensures file ownership is correct and that absolute paths (e.g. plugin `installPath` values in `installed_plugins.json`) resolve identically inside and outside the container. The entrypoint also recursively chowns the home directory (skipping bind-mounted host paths discovered via `/proc/self/mountinfo`) so that files created as root during `docker build` are owned by the runtime user. **It runs as root on EVERY start, so it trusts nothing from the container environment (CS-IMG-067):** its shebang is `#!/bin/bash -p` (no `BASH_ENV`/`ENV`, no imported functions or `SHELLOPTS`), its first lines save the session `PATH`, set `PATH=/usr/sbin:/usr/bin:/sbin:/bin` (the image PATH puts the user-writable `~/.local/bin` and `venv/bin` ahead of `/usr/bin` — a session-planted `awk` would otherwise run as root on a `docker start` of a stopped container) and unset `LD_PRELOAD`/`LD_LIBRARY_PATH`/`LD_AUDIT`/`GCONV_PATH`/`LOCPATH` (never restored: the loader and glibc honour them for gosu and every root-run tool before the privilege drop); the session PATH is restored right before `exec /usr/sbin/gosu … /opt/claude-sandbox/bin/claude-sandbox pidslot`, both absolute. **It is idempotent on a restart (CS-IMG-068):** the user to operate on is resolved by name (`claude`, else the already-renamed host user), the remap/rename run only when something differs, the home relocation only while `/home/claude` is a real directory (not the symlink the first run left), and the home chown, like the venv chown, lists only entries not already owned and uses `chown -h` (find selects a link by its own owner; a following chown would hand a build-time `~/.local/bin/x -> /usr/bin/tool`'s TARGET, which the root part runs, to the session user) — so any second start of the same container does nothing as root that the first did not. It stays although the kept containers it was built for (`--keep`) were dropped: the root part must never assume a first start.
- **Home directory convention:** The base image provides `/home/claude` as the home directory. Child Dockerfiles should use `/home/claude` (not a hardcoded host path like `/home/yourname`) for portability. Use `USER claude` for `RUN` steps that create files under the home dir, and end with `USER root` so the entrypoint has privileges for UID/GID remapping. At runtime, the entrypoint moves build-time files from `/home/claude` to the host home path (e.g. `/home/rt`), skipping anything already present (bind mounts are never overwritten), then symlinks `/home/claude → $TARGET_HOME` so hardcoded paths still resolve.
- **Container naming (`imagebuild.ProjectSlug`):** `claude-sandbox-{parent}-{base}-{h6}-{instance}` (ralph: `…-{h6}-ralph`, no instance). The basename alone used to name the container, so the dozens of directories that share a name in a workspace all collided and only one could run. The parent segment keeps the common case readable; the `h6` digest of the absolute path makes every case correct. `Slug()` remains the plain character normalizer. That absolute path is always the **physical** one — `resolveProjectDir` evaluates symlinks on the `PROJECT_DIR` and working-directory branches alike (CS-LNCH-048), so a checkout reached through a symlink is one project with one slug, one instance-noun pool, one fingerprint and — because the same-path mount uses it — one Claude Code transcript slug rather than a split history `--resume` cannot see across; the config/env cascade walk and the child Dockerfile parent search climb the physical parents, so a workspace-level `.claude-sandbox/` beside the symlink is not seen; the launcher prints `Project: <physical> (resolved from <logical>)` when they differ.
- **Host directories (`internal/hostdirs`, `spec/host-dirs.feature`, CS-DIR):** the one place that names the launcher's per-user dirs and classes them. **Cache** (a cleaner may delete it any time, even under running sessions; rebuilt automatically — plus the locks and one-shot status files beside it) → `CacheRoot` = `~/.cache/claude-sandbox` (`XDG_CACHE_HOME` deliberately not honoured; `launch.SandboxHomeRoot` is `hostdirs.CacheRootRel`). **State** (cannot be rebuilt from another store) → `StateRoot` = `$XDG_STATE_HOME/claude-sandbox` only when that is ABSOLUTE (XDG spec: a relative value is ignored), else `~/.local/state/claude-sandbox`; never mount `StateRoot` or a parent of it into a container. `PeersRoot` = `~/.local/state/claude-sandbox-peers` is the shared peer registry's root — a sibling of `StateRoot` pinned to `$HOME` with no env lookup (it must be the same path on the host and in every container, and no container bind may lie under `StateRoot`); `LegacyPeersRoot` = `~/.cache/claude-sandbox/peers` is where it was, used only during the drain (see Shared peer registry) and never deleted by the launcher. `CheckOwnedDir` is `EnsureOwnedDir`'s refusals without side effects (the drift check's, CS-DIR-019). `EnsureOwnedDir(dir, mode, *Ops)` is the one owned-directory rule — `MkdirAll` as the invoking user, then `Lstat` BEFORE any chmod refusing a symlink, a non-directory and another uid's dir, then chmod to the mode (`Ops.Chmod`/`Ops.Getuid` seams); `mkOwnedPeerDir` is a thin wrapper, so CS-LNCH-107's texts are its errors. `InSandbox(getenv)` is `CLAUDE_SANDBOX_PROJECT_DIR != ""` alone — never `/.dockerenv`, which marks any container (CI included); in a sandbox `StateRoot` is container-local, so state consumers skip or refuse. `Env.StateDir`/`stateDir()` is the test seam, panicking under `go test` when unset like `Env.CacheDir`. Its users are `claude-sandbox global-config migrate|revert|accept` (`StateRoot/global-config/<key>/`, CS-GCFG-053), which refuses in a sandbox, and the launch health check's snapshots in the same store (CS-GCFG-001..015), skipped in a sandbox.
- **Multi-session (`internal/sessions`):** a project can host several sessions. Discovery is by **container label**, never by parsing names (they are lossy — normalized and hashed), which also decouples discovery from the naming scheme. One label-filtered `docker ps --format '{{.Label "..."}}'` yields names, status and all labels with no per-container `inspect` (the `sessions` subcommand then runs ONE batched `docker inspect --format '{{.Name}} {{.State.OOMKilled}}' <names…>` for its OOM marker — `sessions.MarkOOM`, skipped for an empty list, never an error; its stdout is parsed even on a non-zero exit, since docker prints the containers it found before failing on one removed since the ps — and attach/join inspect only the chosen container for their OOM note, CS-SESS-061..063; `docker ps --format` cannot read `State.OOMKilled`, which is sticky on a running container); `docker top` adds the live-claude count so joined sessions are visible; the attachable process is found by matching those pids against `State.Pid` (PPID is the shim for all of them and the TTY column is `?` unless `-t`). Instance nouns are sampled **without replacement** from the nouns not already in use by the project, which is why a 128-word list needs no numeric tail. Three mechanisms, with different durability: a new container (PID 1, reattachable, survives terminal loss), a joined session (`docker exec`, cheap, **unrecoverable** and dies with the container's primary because of `--rm`), and attach (`docker attach`, recovery path). **Launch reservation (CS-SESS-048..054, CS-LNCH-057):** a new container is never `docker run`; every launch (interactive, ralph, `--branch`, the `[b]` fork) runs `docker create` with the full flag set (`Plan.Reserve`/`CreateArgs`), then runs `docker start -ai --detach-keys=K <name>` (`Plan.StartCmd`; measured identical to `run` for stdio, exit code, SIGTERM cleanup and `--rm`) as the session child (below). The split exists because nouns and pid classes are picked from discovery and a container was invisible to discovery until `docker run` had it running, so two concurrent launches could pick one noun (the second failed on the name) or one class (silently overwriting a peer-registry record). The picks and the create run in one critical section under a host-wide `flock` on `~/.cache/claude-sandbox/launch.lock` (`launch.FileLock` behind the `launch.HostLock` seam, `Env.Lock`; host-wide because classes are): `DiscoverAll`, remove `created` containers older than 60 s (orphans of a launcher that died between the steps — `--rm` never fires for a container that never started; plain `docker rm`, never `-f`), re-validate the EARLY noun (picked before the image build because it names the worktree in the banner; re-picked, with name/label/worktree re-derived and the banner reprinted, when a concurrent launch took it; `--worktree=NAME` and ralph's fixed name keep theirs), pick the class, `docker create`; discovery there is `DiscoverAllUncounted` (no per-sandbox `docker top` in the critical section). Released after create and before the start (the fd is also `O_CLOEXEC`, Go's default, so the docker child never holds it), and **never held across image builds**. A create `Conflict` (a non-locking actor) re-picks and retries, 3 attempts total, then exits 2; ralph fails on the first unless the holder is itself a `created` reservation older than 10 s (a `docker start` that failed — the launcher does not clean those up), which is removed and retried once; a younger holder may be a concurrent launch between its create and its start (the lock is released before the start), so it is never removed (`sessions.Inspect`, `docker inspect --type container`, `{{.Created}}` is RFC 3339, not the ps layout). Only docker's name conflict (`Conflict. The container name`) counts — a bare "Conflict" would match `Conflicting options` flag errors. A lock that cannot be taken in 30 s warns and launches unserialized; the warning says names stay unique but pid classes (and, during the peers drain, the peer registry root) are unprotected. The lock is host-wide only for launches run ON THE HOST: `~/.cache/claude-sandbox` itself is not mounted into sandboxes (only subdirectories — package caches, the peer registry), so launchers run inside different containers take different lock files; names stay unique through the create conflict retry, but pid classes can collide between concurrent in-sandbox launches (found in the live verification). Discovery is `docker ps -a --filter status=created --filter status=running --filter status=paused --filter status=exited` (paused because plain `ps` always listed them — dropping them would free a paused session's pid class; `{{.State}}`/`{{.CreatedAt}}` and the later labels are optional trailing fields, and CreatedAt is parsed from its first three fields only, since zones without a letter abbreviation render it numerically, e.g. `+1030 +1030`), so reservations count as in use for both pickers, while `Session.Reserved()` keeps them out of every candidate list (`Interactive`), the `sessions` listing (`Live`) and `docker top`. **Exited rows (CS-SESS-070):** every sandbox container is `--rm`, so an `exited` row (State, or a stateless row's `Exited` status) is one docker is removing: `list` drops it — never listed, never a candidate, no noun or pid class held, no `docker top` — and only `DiscoverForLaunch` returns it apart, for the peers-root pin. `restarting` is never asked for (no restart policy). The `sessions` table has a `STATE` column (`running`/`paused`, `-` for a stateless row; `--json` `state`, CS-SESS-074). Kept containers (`claude-sandbox.keep`, CS-SESS-072/073, CS-DIR-016) were dropped with `--keep`; those IDs are retired, and the label's ps `--format` slot is an empty field so later field indexes did not move. **Shadow directories (CS-LNCH-080..084, `internal/launch/shadowdir.go`):** each launch's shadow files live in one `os.MkdirTemp(<Env.TempRoot or $TMPDIR>, "claude-sandbox")` directory that the launcher removes itself only once it saw the container's `die` (CS-LNCH-094; not after a detach, a signal-initiated exit or a killed launcher), so the container carries a `claude-sandbox.shadowdir` label (outside the config hash — labels are never hashed) and `reserveContainer` sweeps after the first discovery, under the lock (`launch.PruneShadowDirs`): only `^claude-sandbox[0-9]+$` entries that `Lstat` as real directories owned by `os.Getuid()`, older than `ShadowDirMinAge` (1 h), not the launch's own, and whose base name no container names — one `docker ps -a --no-trunc` with NO filter, `{{.Label "claude-sandbox.shadowdir"}}` plus `{{.Mounts}}` (bind sources; covers exited containers, pre-label launchers and other sandboxes' temp roots, matched by base name so a different spelling of the root only ever keeps a dir), run only when a candidate exists; a failed listing removes nothing; every failure is one warning. A candidate whose `RemoveAll` fails part-way is renamed `<dir>.unremovable` (`setAside`; the name leaves the sweep's pattern, so it warns once, not on every launch — headless probes included), or, if that rename fails, has its mtime set to now (backed off one `ShadowDirMinAge`). The directory is made AFTER the lock is taken (it used to be made before the up-to-30 s wait), so a lock holder never sees an in-flight launch's directory; the age covers lockless and older launchers. `reserveContainer` removes its own directory on any error return; `startReserved` removes it after a `docker start` that could not be run only once `docker rm` of the reservation succeeded (a surviving container may still mount it); `wouldBeFingerprint` builds into a private directory and removes it. **Nested launches (CS-LNCH-161/162):** a bind source resolves on the host, so a launcher inside a sandbox (`hostdirs.InSandbox`) never uses the container's own temp root — docker would mount empty root-owned host paths in place of the CLAUDE.md/.mcp.json/gitconfig shadows. `launch.NestedShadowRoot` (via `Env.shadowRoot`, resolved in `launchWith` before any image build, passed to `reserveContainer`): a non-empty `TMPDIR` as is (the operator's statement) unless it is relative or its covering mount in `/proc/self/mountinfo` (longest mount point, octal escapes decoded, `Env.MountInfo` seam — fixtures fake it, nil under go test panics) is `/` or a tmpfs — definitely container-local, exit 2; an unreadable mountinfo trusts it; else `<CLAUDE_CODE_TMPDIR>/claude-sandbox-shadow` (`hostdirs.EnsureOwnedDir`, 0700) when `CLAUDE_CODE_TMPDIR` is absolute and under the config dir (retried symlink-resolved) — the one dir the outer sandbox is known to same-path mount (CS-LNCH-008) and where it derives that variable (CS-LNCH-034) — else exit 2 naming the reason and `TMPDIR`. Refuse, not fall back: the old fallback was the silent loss. The env-file copies (CS-LNCH-132) were never affected — the docker CLIENT reads `--env-file`. The sweep runs over the resolved root (`filepath.Dir(own)`); the HOST launcher (not in a sandbox) also sweeps `<d>/claude-sandbox-shadow` for its own absolute `CLAUDE_CODE_TMPDIR` and for `<config dir>/tmp` (CS-LNCH-166, `nestedShadowSweepRoots` in `reserve.go`; a root that does not `Lstat` as a real dir the user owns is skipped; under go test a root the real environment — or a real home's default `~/.claude` — would sweep panics); a nested `TMPDIR` root is swept only by nested launches. **Other resolved bind sources (CS-LNCH-163..165, `internal/launch/nested.go`):** nested, `Inputs.nestedBindSourceOK` admits a path only when `Inputs.MountInfo` (`Env.MountInfo`, passed by the launch AND `wouldBeFingerprint` so drift agrees; nil under go test panics, read only when a check is reached) is readable and the path's covering mount is neither `/` nor tmpfs — stricter than CS-LNCH-162 (unreadable = not visible); mountinfo's root field is NOT consulted (btrfs subvolume names — Fedora `/root/...`, Ubuntu `/@home/...` — make a same-path test unreliable), so a bind of a different host path is not caught. Applied only where a `-v` would actually be added (after the same-path-cover checks): the settings.json symlink target (skip + one WARNING, runs without user settings), the linked worktree's common dir (skip + one WARNING, launch goes on — only the mount; the cascade/Dockerfile reads through the main checkout are client-side), and the peers root — the one the launch CHOSE (also admitted when the launcher's `XDG_RUNTIME_DIR` cleans to it — the outer is bridged to it; else the whole bridge stands down before anything is created, key-off argv and hash, `peerroot=none`; so a nested launch under an unbridged sandbox no longer bridges, CS-DIR-027/028). The drift check's private dir is never mounted and stays container-local. Tests set `Env.TempRoot` to a scratch dir (every test `Env`, the init fixture's included — it once swept the real `/tmp` against a faked empty `docker ps`) — a test launch must never sweep the real temp root. `docker exec` needs `-u` (it skips the entrypoint's gosu and the image ends `USER root`) but not `-w` (inherited via `Config.WorkingDir`). **Session child and OOM report (CS-LNCH-085..094, CS-SESS-059/060, `internal/oomreport`, `cmd/claude-sandbox/session_child.go`):** the launcher never execs docker — every interactive path (`docker start -ai` for new/ralph/`--branch`/headless, `docker attach`, a join's `docker exec`) goes through `execx.Runner.RunSession`, a child in the launcher's own process group (the TTY keeps delivering keys and job-control signals to docker; no `Setpgid`) that the launcher waits on, passing the status through (128+n for a signal). SIGTERM/SIGHUP are forwarded; SIGINT/SIGQUIT are CAUGHT, never `signal.Ignore`d — SIG_IGN survives exec and docker would inherit it — and dropped only when the launcher is its terminal's foreground group (`tcgetpgrp(/dev/tty) == getpgrp()`; no `/dev/tty` = not foreground), since the terminal already hit docker; otherwise (`kill -INT <pid>` from a supervisor) forwarded. Signals inherited as SIG_IGN (`nohup`) are not caught (`signal.Ignored`). The handlers stay installed until `SessionResult.Done()` after the report; signals in the die wait arrive on `Late` and end it silently (CS-LNCH-097). `Pdeathsig: SIGKILL` with `runtime.LockOSThread` for the child's life (Linux fires it when the forking THREAD exits); `session_other.go` omits it so darwin still builds. Why: with `--rm` the container is gone before an inspect after exit could read `OOMKilled`, so before the child starts `oomreport.Start` subscribes to `docker events --since <now> --filter container=<name> --filter event=oom --filter event=die --filter event=kill --filter event=stop` (kill/stop only feed `Outcome.OutsideStop`, set when one arrives before the die — never a report; CS-TMUX-071) (through `Runner.Start` with `Cmd.DieWithParent` — own pgrp plus Pdeathsig from a locked thread, CS-LNCH-098 — so `execx.Fake` scripts the stream: stub output is the stream, and its end reads as a detach at once). docker's `container=` filter is a PREFIX match, so events are kept only when `Actor.Attributes["name"]` equals the container (CS-LNCH-095). A reserved start is followed by `sessions.Inspect`: still `created` = never ran → `docker rm` + shadow dir now, no die wait (CS-LNCH-096). A primary session waits ≤2 s (`DieWait`) for `die` (then ≤150 ms `OOMGrace` for an oom trailing a die 137): none → detached, silent; die 137 + ≥1 oom → the five-line report; oom but another death → one soft `note:` line. Both name BOTH causes (the container's memoryLimit or the host running out of memory, CS-LNCH-089/090), as do the `(OOM)` legend and the attach/join note (CS-SESS-061/063): docker's `oom` event is containerd's TaskOOM, which its cgroup v2 watcher (`pkg/oom/v2`) publishes on any rise of the container's `memory.events` `oom_kill` — a counter of kills "by any kind of OOM killer" (cgroup-v2.rst), the host's global one included, which CS-LNCH-112's `--oom-score-adj` aims at sandboxes — and `State.OOMKilled` is set from that event; the `oom` counter that rises only at the container's own `memory.max` is removed with the `--rm` container. The report's last line points at the host kernel log (`journalctl -k` or `sudo dmesg`, may need sudo; `Memory cgroup out of memory` = a cgroup limit, plain `Out of memory` = global). A join keys off the exec's own 137 plus an oom in its window (a die ends that wait early; `OOMGrace` otherwise). A forwarded signal skips the wait and the report (the Paseo SIGTERM contract). The limit and its source ride create-time labels `claude-sandbox.memorylimit`/`memorylimitsource` — read back from the event attributes, which carry every container label, so attach/join never re-resolve — and env `CLAUDE_SANDBOX_MEMORY_LIMIT(_SOURCE)`; neither is hashed (the value already is, as `memory=`; where it is written is not a property of the container). The CS-LNCH-108 stand-downs and the fingerprint's `KindEnv` digests read the same snapshot (the digest keeps the original path); messages and the cascade report name the original paths; an unreadable env file fails the launch (exit 2) before any image work. An env file is the one env channel the launcher passes from a session-writable file at create time; the child Dockerfile and cascade mounts are trusted by design (README's accidental-damage threat model). The `-e` channels the launcher builds itself (`ANTHROPIC_API_KEY`, `CLAUDE_CONFIG_DIR`, the AWS allowlist, the headless `HeadlessEnv` allowlist) are fixed name lists that contain none of these keys, so they need no filtering.

## Ralph Runtime Directory

Ralph stores all runtime files under the resolved ralph directory — `.claude-sandbox/ralph/` (resolved by `internal/paths`). It contains only ephemeral state — never commit its contents directly (it is covered by the host gitignore / sidecar).

```
<ralph-dir>/                        # .claude-sandbox/ralph/
  stop                              # touch to halt the loop (checked each iteration)
  lock                              # PID lock preventing concurrent loops
  runlog.json                       # structured per-iteration metrics (persistent across runs)
  runlogs/                          # raw NDJSON stream logs
    rawlog_<YYYYMMDDHHmmSS>_iter<N> # one file per iteration (persistent)
  temp/                             # scratch space (wiped each iteration)
    quota-status                    # "ok", "quota_exhausted", or "rate_limit"
    stderr                          # captured stderr from claude process
```

- **Stop the loop:** `touch .claude-sandbox/ralph/stop`
- **Run metrics:** `<ralph-dir>/runlog.json` — array of runs with per-iteration duration, tokens, cost, story marker, subagent details, and the loop's classified `outcome` (`ok`, `quota_exhausted`, `rate_limit`, `watchdog_timeout`, `iteration_timeout`, `error`, `oom`; CS-RLP-029). `oom` = claude exited 137 and the cgroup's `memory.events` `oom_kill` counter rose; ralph backs off 60 s and retries the iteration once, then stops (exit 137) and notifies on a second consecutive one (CS-RLP-023..028). Ralph runs inside the container, so it also samples `memory.events` `oom` and words the cause (CS-RLP-030, runlog `oomCause`): `oom` rose = the container hit its memoryLimit; readable and unchanged = a kill from outside the container's memoryLimit (the host ran out of memory, or a parent cgroup's limit), where raising memoryLimit will not help; unreadable = both named. The cause changes only the message, never the back-off/retry
- **Debug a run:** read the corresponding `<ralph-dir>/runlogs/rawlog_*` file for the full NDJSON stream
- **Do not store persistent state in `<ralph-dir>/temp/`** — it is wiped at the start of every iteration
- Prompt files live in the resolved agent directory — `.claude-sandbox/agent/`, e.g. `.claude-sandbox/agent/PROMPT.md` — these are inputs, not runtime outputs

## Python Environment

- Python 3 + venv at `/opt/claude-sandbox/venv` (`VIRTUAL_ENV` env var set, venv bin prepended to `PATH`)

The venv is built as root; the entrypoint chowns its **directories** (not files) to the host UID:GID at every start, which is all pip needs to install, upgrade or uninstall — chowning files would copy each one up on overlay2 (CS-IMG-052). Like the home chown it never touches a bind mount: it runs only when the venv is on the root filesystem and not a mount point, and prunes mount points below it (`-xdev` alone still lists a mount point directory). Both it and the home chown read mount points from `/proc/self/mountinfo` decoded (`\040` = space, `\134` = backslash; each `\` is made `\0` first, since `%b` reads `\0nnn` and would swallow a digit after `\040`) and glob-escaped for `find -path` (`_cs_prune_args`). `pip install --user` fails (the venv hides user site-packages). Installs are per-container and die with it; permanent ones go in the child Dockerfile
- Do NOT use `--break-system-packages` — always install into the venv

## Development Notes

- **Workflow:** spec first (`spec/*.feature`, stable scenario IDs), then Ginkgo tests referencing those IDs, then implementation. Run `go test ./...` and `scripts/check-spec-coverage.sh` before considering a change done. Tests inject `execx.Fake` and `prompt.Scripted` — no docker/git/network in unit tests. Tests never touch the real temp root: every test `Env` sets `TempRoot` (and every `launch.Inputs` a `TempDir`) to a scratch dir, and `launch.shadowRoot` panics under `go test` (`testing.Testing()`) when a shadow directory would be made in or swept from `os.TempDir()` — a forgotten fixture fails loudly instead of deleting live sessions' shadow mounts against a faked empty `docker ps`. Paths whose length matters (the 103-byte peer socket limit, CS-LNCH-055) are built from a short fixed root under `/tmp`, never from `TMPDIR`, so the suite passes under any `TMPDIR`.
- The shim uses `readlink -f` to resolve symlinks and find the repo root; the binary honors `CLAUDE_SANDBOX_REPO_ROOT` (set by the shim) and otherwise derives it from its own location.
- Go deps are plain modules (no `vendor/`). The shim's `docker run golang` path persists `GOCACHE` and `GOMODCACHE` under `bin/dist/` (gitignored) so each dependency downloads once; the Dockerfile builder runs `go mod download` in its own cached layer.
- **Image staleness is a build-inputs fingerprint, not mtimes (CS-IMG-032..036).** Every build stamps `--label claude-sandbox.build-inputs=<sha256>`: base = `Dockerfile` content alone (CS-IMG-048); tools = `Dockerfile.tools` + baked-source contents (`imagebuild.BakedSources` = exactly the context COPY sources of `Dockerfile.tools`, pinned by a parsing test, CS-IMG-037), symlinks below a baked root by target, a baked source that is itself a symlink followed as COPY follows it — only to a target inside the repo (the build context); an outside target fails the build and is never walked (CS-IMG-040), and exec bits ONLY for `imagebuild.ModeBakedSources` — the final stage's COPYs without `--chmod` (`logstream/`, `PROMPT_RALPH.md`; `mcp/discord-notify/` is only bundled), pinned to `Dockerfile.tools` by a parsing test — because every other source is compiled, bundled, embedded or `--chmod`ed and a full-mode hash made a umask-002 checkout rebuild for nothing (CS-IMG-039) (`cmd/`, `internal/`, `go.mod`/`go.sum`, `assets.go`, `scaffold/`, `scaffold-ralph/`, `container-context.md`, `mcp-servers.json`, `logstream/`, `entrypoint.sh`, `PROMPT_RALPH.md`, `mcp/discord-notify/`, `notification-hooks.json`, `bin/setup-lsp-plugins`, `bin/notify-webhook` — each exactly a COPY source path; `_test.go` excluded, CS-IMG-031; `.dockerignore`d debris excluded, CS-IMG-038); CLI = `Dockerfile.cli` content; child = Dockerfile path + content + context + base image ID; cap = generated Dockerfile + parent ID + tools ID + CLI ID. A labeled image rebuilds exactly when the label differs, so editing a source still picks up on the next launch without `--rebuild`. The old rule compared mtimes (and parent Created times) with the image's Created time. A fully cached rebuild leaves Created unchanged, so once a source was newer than the image (a fresh worktree, a pull, a touch), every launch rebuilt it again, and interactive launches also paid `WarnCacheBudget`'s ~8 s `docker system df` (since detached, CS-IMG-041). Parent IDs instead of Created times also catch a parent switched back to an older-built image. Unlabeled images, and fingerprints that cannot be computed (unreadable file, missing parent ID), fall back to the old time rule (CS-IMG-035); an uncomputable tools fingerprint warns, since that fallback can bring back a rebuild on every launch. `--rebuild` rebuilds all five regardless of labels (CS-IMG-002). Deliberately not inputs: the `CLAUDE_SANDBOX_VERSION` stamp and the Claude Code pin, which the update check owns. The label changes the image config, so a base's first labeled build cache-misses its children once. A CLI update rebuilds nothing but the CLI image and the caps; a baked-source commit nothing but the tools image and the caps. The tools split changed the base fingerprint, so each base (and child) rebuilds once after upgrading. `fingerprintVersion` v2 (CS-IMG-039/040) changed every base fingerprint, so each labeled base (and so each child) rebuilds once after upgrading.
- **Cache mounts and `--no-cache`:** a build run with `--no-cache` gets a FRESH cache mount, not the shared one — verified on Docker 29.3/BuildKit 0.28 (three ordinary builds accumulate state in one mount id; the same builds under `--no-cache` each start empty). So `--rebuild` discards the shared apt/pip/npm/go caches by design (CS-IMG-002). This, not GC, explains most "the cache mount was wiped" reports — check for `--no-cache` before investigating budgets.
- **Host-side hygiene:** two independent GC limits govern cache mounts — the `All: true` rule's total budget (pruning helps) and the `type==exec.cachemount` rule's cap (pruning does NOT help; it is a setting). `WarnCacheBudget` reports them as separate messages for that reason. The README "BuildKit cache" section carries the `docker builder prune -af` and the explicit `builder.gc.policy` recipe; `defaultKeepStorage` is the Desktop-era key and is ignored on engines that derive thresholds from disk size, and `builder.gc` needs a full daemon restart (SIGHUP does not reload it).
- **`packageCaches` lever** (`hostAccess.packageCaches` / `--package-caches`): mounts `~/.cache/claude-sandbox/{go-mod,go-build,npm,pip}` writable at the same path and sets `GOMODCACHE`/`GOCACHE`/`npm_config_cache`/`PIP_CACHE_DIR`. The launcher creates them with `hostdirs.EnsureOwnedDir` (0700, tightening an existing wider one; symlinks and foreign owners refused) before `docker create` (Docker would create a missing bind source as root and the entrypoint never chowns mount points); a dir it cannot own leaves that cache out with one warning, never failing the launch (CS-LNCH-156). Assembled after the cascade mounts: a same-path mount already covering a dir is kept, not doubled (CS-LNCH-157). Nested (`hostdirs.InSandbox`), a cache is mounted only when the launcher's own toolchain variable, path-cleaned, names its dir — the outer sandbox's mount is the only evidence the host dir exists and is the user's — else one `Note:` and no mount/`-e` for it (CS-LNCH-155, the CS-LNCH-137 precedent). An env file defining a cache's variable (`envFilesDefine`, bare keys counting when the launcher's environment sets them) skips that cache whole — no `-e`, no mount, nothing created or printed — since `-e` beats `--env-file` (CS-LNCH-159, the CS-LNCH-135 rule per cache; checked before the home check, so four env-file caches never reach it). A non-absolute home stands all four down with one warning (panics under `go test`, as does the real home, before anything is created or re-moded — `cacheHomeUsable`, shared with the pre-commit cache; CS-LNCH-158). The root is fixed (`launch.PackageCacheRoot`) and must never be pointed at the host's own caches — Go trusts extracted module dirs, so a session could otherwise poison the host toolchain.
- **pre-commit cache (CS-LNCH-133..139, operator decision 12):** always on, no key — every `Build` (interactive, ralph, headless, `--branch`, `--detach`) mounts `~/.cache/claude-sandbox/pre-commit` (`launch.PreCommitCacheDir`) rw at the same path and sets `PRE_COMMIT_HOME` to it, because `$HOME` is the host's and pre-commit hook envs are bound to the interpreter that built them (image python3.11 vs host python3.13), so a shared `~/.cache/pre-commit` rebuilt on every alternation. The image's Python is deliberately NOT aligned with the host. The dir is `hostdirs.EnsureOwnedDir` (0700, never through a symlink or another uid's dir); a failure warns once and launches without it (never fails the launch). An env file defining `PRE_COMMIT_HOME` (`envFilesDefine`, the CS-LNCH-108 reader — a bare line with the host var set counts) wins silently: no `-e`, no mount, nothing created. The launcher's own `PRE_COMMIT_HOME` is never forwarded (it names the host cache — the collision); a bare env-file line is the explicit pass-through. In a sandbox (`hostdirs.InSandbox`) it applies only when the launcher's own `PRE_COMMIT_HOME`, `filepath.Clean`ed, equals the dir — the outer launcher's mount is the evidence the host dir exists and is the user's; otherwise one `Note:` and nothing (docker would create the host dir as root). A non-absolute (or empty) home stands it down with one warning (CS-LNCH-138). It is assembled AFTER the cascade mounts: a same-path mount already covering the dir (the dir or a parent) is kept and no second `-v` is added — `-e` still set, a `:ro` cover warns (CS-LNCH-139). Under `go test` a non-absolute home, or one that is the real home (`os.UserHomeDir` OR `user.Current().HomeDir` — HOME can be unset under `env -i` while `hostIdentity` falls back to the user database), panics before anything is created. It reaches the drift fingerprint only through the normalized mount set, so every container launched before it drifts once.
- **Version stamping:** the launcher computes `git describe --tags --always` + `-dirty` when `git diff-index --quiet --ignore-submodules=all HEAD --` exits 1 (CS-IMG-005; never `describe --dirty`, whose index refresh runs filter programs, a submodule's included — so a stat-only change can read dirty and submodule changes do not; every call bounded, CS-IMG-076: a timeout of any = `unknown` + one warning) and passes it as the `CLAUDE_SANDBOX_VERSION` build-arg to the **tools** build (the base has no version, so a new stamp never changes its ID). `Dockerfile.tools` bakes it into `/opt/claude-sandbox/version` and the `org.opencontainers.image.revision` label; the cap turns that label into `ENV CLAUDE_SANDBOX_VERSION` (CS-IMG-005). The stamp is not a fingerprint input, so a commit that touches no baked source leaves the tools image, and its label, as they were. `claude-sandbox --version` prints the host-script version and the tools image's baked version, noting a difference without promising a rebuild: the stamp is not an input, so the tools image catches up only when a baked source changes.
- Missing `.claude-sandbox/env` (no level of the cascade has one) logs a warning but doesn't fail; when the project's own `env.example` exists it is a single `Note:` line instead (CS-LNCH-056).
